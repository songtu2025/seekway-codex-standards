# SEEKWAY Web 界面开发标准

- 规范版本：V1.3.0
- 适用范围：公司内部和后台业务系统
- 视觉基线：SEEKWAY 退货语义分析智能体
- 默认技术栈：React 18 及以上、TypeScript、Vite、Ant Design 6
- 维护负责人：待填写
- 最后更新：2026-09-08

本标准适用于后台界面的设计和开发。现有项目保留已验证的设计系统，并在“项目配置”中记录差异，不为套用默认值进行全量重构。

## 1. 项目配置

项目负责人填写本节；未填写的项目采用默认值。

- 公司品牌名称：`SEEKWAY`。
- 品牌主色：默认 `#12765B`。
- UI 组件库：新项目默认 Ant Design 6；现有项目填写已验证的组件库，不得自动迁移。
- 图标体系：新项目默认 `@ant-design/icons` 6；同一项目只能使用一个主要业务图标体系。
- 默认语言：简体中文。
- 默认时区：待填写。
- 主要设计视口：默认 `1440 × 900`。
- 最小支持视口：默认 `1024 × 640`。
- 是否支持移动端：默认否。
- 公司设计系统：[SEEKWAY Web UI Kit V1.2.0](https://www.figma.com/design/eed9GukOv7zM7n04Lu1xUl)。
- 项目设计稿或设计系统地址：待填写；没有时使用公司设计系统。
- 允许的项目差异：待填写。

## 2. 规则优先级

发生冲突时按以下顺序执行：

1. 用户明确提供的设计稿和验收标准。
2. 本项目填写后的界面规范。
3. 项目已有设计令牌、基础组件和相似页面。
4. 本标准的默认规则。

设计稿不得覆盖业务、权限、安全和可访问性要求。规则冲突时，必须说明并等待确认。

## 3. 设计原则

1. **操作高效**：减少查找、录入、比较和批量处理的步骤。
2. **保持一致**：相同概念使用相同名称、位置、组件和交互，不为单个页面另设规则。
3. **层级清晰**：一个页面只有一个主要标题，一个操作区域最多只有一个主按钮。
4. **密度适中**：默认使用中等信息密度；高频数据页面可更紧凑，但不能影响阅读和操作。
5. **状态完整**：覆盖正常、等待、无数据、失败、禁用和操作反馈。
6. **减少装饰**：普通后台功能不使用大面积渐变、装饰性插画、玻璃拟态、大标题或大留白。

## 4. 设计令牌

采用公司基线时，只使用 Ant Design Token 和 SEEKWAY 扩展令牌，不得散落无语义的视觉数值或建立第二套主题。现有项目使用原主题系统中的等价令牌。

新项目复制 `templates/seekway-antd-theme.ts` 和 `templates/seekway-theme.css` 到对应的前端路径。前者是 Ant Design 组件令牌的唯一来源；后者只维护侧栏和页面布局等扩展，并在全局入口导入一次。两者不得定义同一令牌。现有项目继续使用原主题配置，只映射 SEEKWAY 语义。

必须在应用根节点启用中文环境和 SEEKWAY 主题：

```tsx
import { App as AntdApp, ConfigProvider } from "antd";
import zhCN from "antd/locale/zh_CN";

import { seekwayAntdTheme } from "./theme/seekway-antd-theme";
import "./styles/seekway-theme.css";

<ConfigProvider locale={zhCN} theme={seekwayAntdTheme}>
  <AntdApp>
    <Root />
  </AntdApp>
</ConfigProvider>;
```

通用交互使用 Ant Design 组件。自定义 React 区域通过 `theme.useToken()` 获取颜色、字体、圆角和阴影；CSS 只引用 `seekway-theme.css` 中的布局扩展变量。DatePicker、Calendar 等日期组件须配置 Day.js 中文环境；项目直接导入 Day.js 时必须将其声明为直接依赖。

### 4.1 颜色

必须遵守：

- 颜色按用途命名，不用 `blue-500` 等视觉名称表达业务用途。
- Cover 与应用侧栏使用 `--gradient-sidebar`；渐变起点由 `--color-surface-sidebar-start` 统一管理。
- 侧栏悬停使用半透明的 `--color-surface-sidebar-hover`，不得重新硬编码固定深色。
- 状态颜色必须同时配合文字、图标或形状，不得只用颜色区分成功、警告和失败。
- 警告图形使用 `colorWarning`，小号警告文字使用 `colorWarningText`；现有主题使用等价令牌。
- 正文和占位文字与背景对比度不低于 `4.5:1`；大号文字以及承载控件边界、状态或含义的图标、边框和焦点指示不低于 `3:1`。
- `colorBorderSecondary` 或等价令牌只用于无语义的分隔线；输入框等控件边界使用 `colorBorder` 或对比度更高的组件 Token。
- 禁用状态不能只降低透明度到无法辨认，仍须保留内容可读性。

### 4.2 字体

- 页面标题使用 `28px`，卡片或分区标题使用 `18px` 或 `20px`，正文默认 `14px`。
- 正文、输入内容和主要操作文字不得小于 `12px`；输入内容默认使用 `14px`，不得照搬参考项目中的 `10px` 小字号。
- 未提供 Inter 或 Noto Sans SC 字体文件时使用系统回退字体，不得自行增加远程字体或生产依赖。
- 正文默认使用常规字重，标题和需要强调的信息使用中等或半粗字重。
- 表格数字使用等宽数字特性；长编号、哈希和代码可使用项目批准的等宽字体。
- 不得仅靠字号表达层级，还应结合间距、字重和位置。

### 4.3 间距、尺寸和圆角

- 使用 `4px` 基础网格，只能从令牌中选择间距。
- 同一表单、筛选区或操作区中的控件高度必须一致。
- 默认控件高度为 `38px`，紧凑控件为 `34px`；主要表单、触摸场景或重要操作可使用 `40px`。
- 圆角用于表达组件边界，普通按钮、标签和输入框不使用胶囊形状。
- 普通记录使用 `48px` 基准行高；包含摘要、状态和操作的复杂业务记录可使用 `84px`，不得机械压缩成单行。

### 4.4 阴影、层级和动效

- 默认通过背景和边框区分层级，阴影只用于浮层、弹窗、抽屉和悬浮控件。
- 轻量浮层使用 `boxShadow`，弹窗和大型浮层使用 `boxShadowSecondary`；现有主题系统使用其等价语义令牌。
- 层级统一由项目的 `z-index` 令牌管理，业务组件不得使用任意超大数值。
- 普通过渡时长使用 `120–200ms`，弹窗和抽屉使用 `200–300ms`。
- 动效不得阻塞操作，不为纯装饰循环播放；必须支持 `prefers-reduced-motion`。

## 5. 页面骨架与布局

### 5.1 默认页面骨架

后台页面按以下顺序组织：

```text
全局导航
└── 页面主体
    ├── 面包屑（需要表达层级时）
    ├── 页头：标题、说明、主操作
    ├── 筛选或查询区
    ├── 批量操作和辅助操作
    ├── 数据或表单内容区
    └── 分页、结果说明或提交操作
```

Figma 的 `04 Page Templates` 只提供骨架和组件组合参考，不是运行时依赖，也不要求整页复制。现有项目继续使用原布局。

- 页面主体使用 `--page-padding`，桌面基线为 `32px`；响应式调整集中在主题层，不在业务页面硬编码。
- 页面一级区块间距默认 `16px`；只有需要明确分组时使用 `24px`。
- 一个页面只保留一个主标题；面包屑只用于真实层级，不重复展示首页入口。
- 数据密集页面使用 `layout-wide-max`，长流程使用 `layout-workflow-max`，阅读和窄表单使用 `layout-narrow-max`。
- 只在内容具有独立边界、背景或操作范围时使用卡片。

### 5.2 响应式

- 默认以 `1440 × 900` 设计；必须检查 `1024 × 640`、`1280 × 720`、`1440 × 900`、`1920 × 1080`，以及浏览器 `125%` 和 `150%` 缩放，关键操作均须可完成。
- 小于 `1200px` 时，侧栏收缩为 `72px` 图标导航，并收起顶部栏次要文字；图标仍须保留可访问名称和可见提示。
- 最小视口允许内容区纵向滚动，但主操作不得消失，页面不得出现横向滚动。
- 数据表格确需横向滚动时，滚动只能发生在表格容器内；关键标识列和操作列应按需要固定。
- 表单在空间不足时从双列变为单列，标签和控件不得相互覆盖。
- 没有移动端要求时不设计移动端导航和交互，但窗口缩放不得遮挡内容或隐藏关键操作。

### 5.3 应用壳层与登录页

- 桌面端默认使用 `236px` 深色侧栏和 `68px` 顶部栏；侧栏承载品牌、一级导航、系统入口和运行状态。
- 顶部栏承载全局搜索、关键容量或任务状态、当前用户和退出入口，不放页面级筛选条件。
- 当前导航使用主色浅底、左侧强调线或等价方式高亮；任意时刻只能有一个一级导航处于当前状态。
- 登录页可使用左右品牌分栏，默认比例为 `1.1fr / 0.9fr`，左侧最小 `520px`、右侧最小 `470px`；业务页面不得沿用登录页的大标题和大面积品牌背景。
- 品牌名称统一显示为 `SEEKWAY`；项目名称和产品名称另行展示，不使用未经确认的品牌后缀。

## 6. 导航与页面标题

- 导航名称使用稳定的业务名词，不使用临时活动文案。
- 同级导航按业务频率或流程排序，不按开发模块随意排序。
- 当前导航项、展开项和焦点项必须可区分。
- 页面标题描述当前对象或任务，例如“订单管理”“编辑供应商”，不用“欢迎使用”。
- 返回操作必须回到用户可预期的位置，并尽量保留列表的筛选、分页和滚动状态。

## 7. 按钮与操作

- 一个操作区域最多一个主按钮，用于当前最重要且安全的下一步。
- 普通次要操作使用默认按钮或文字按钮；危险操作使用明确的危险样式。
- 按钮文案使用“动词 + 对象”，例如“新建订单”“保存配置”，避免只有“确定”“处理”。
- 同一组按钮顺序保持一致；项目采用的组件库已有顺序时遵循组件库。
- 提交期间显示处理中状态并阻止重复提交，完成后给出明确成功或失败反馈。
- 图标按钮必须有可访问名称和提示。
- 低频操作超过三个时收纳到“更多”菜单；高风险操作不得与高频主操作紧邻且样式相同。

## 8. 表单

- 每个控件必须有持久可见的标签，占位文本不能替代标签。
- 常规表单默认标签在控件上方；短且稳定的字段可使用统一宽度的左侧标签。
- 必填标识、帮助信息和错误信息的位置在整个项目中保持一致。
- 在用户离开字段或提交时校验；错误信息必须说明问题和修复方式，并与字段关联。
- 保留已输入的有效内容，不因单个字段错误清空表单。
- 选择控件选项较少且需要对比时使用单选；选项较多时使用选择器并支持搜索。
- 开关只用于立即生效的二元状态；需要保存后生效时使用复选框或明确的表单提交。
- 日期、金额、百分比等字段在标签或后缀中明确格式和单位。
- 保存、取消等操作的位置应稳定；长表单可使用吸底操作栏，但不得遮挡内容。

## 9. 表格、列表与数据展示

- 文本默认左对齐，数字和金额右对齐，状态可居中；同类列必须统一。
- 表头表达数据含义和单位，不把筛选条件、帮助说明全部塞入表头。
- 默认行高 `48px`，高密度页面可使用 `40px`；表头高度保持一致。
- 操作列放在末尾并保持稳定，常用操作直接展示，低频操作收纳到菜单。
- 排序、筛选和分页状态必须可见；返回列表时应尽量保留用户状态。
- 空数据必须区分“尚无数据”和“筛选无结果”，分别提供创建或清除筛选的下一步。
- 加载时使用骨架、局部加载或进度提示；局部刷新不得阻塞无关区域。
- 批量操作必须显示已选数量，并在执行前说明作用范围。
- 金额、比例、日期和枚举状态统一格式化，不直接展示后端原始代码或 `null`。
- 默认分页适用于可增长的数据集合；只有数据量已知且很小时才一次性展示全部数据。

## 10. 反馈、弹窗与异常

- 立即完成的轻量结果使用消息提示；需要处理的异常保留在相关区域。
- 错误信息不得暴露堆栈、数据库信息或内部错误码，可以提供脱敏追踪编号。
- 弹窗只用于需要打断当前流程的确认或短任务；复杂编辑使用独立页面或抽屉。
- 弹窗打开后焦点进入弹窗，关闭后返回触发元素，并支持键盘关闭；危险确认应防止误触。
- 删除、覆盖、停用等操作必须说明对象、影响范围和是否可恢复，按钮文案应写明具体动作。
- 全页失败提供原因说明和重试路径；局部失败只影响对应区域，不应清空其他成功内容。

## 11. 页面状态

每个数据页面至少包含：

1. 首次加载。
2. 正常数据。
3. 尚无数据。
4. 筛选无结果。
5. 请求失败并可重试。
6. 无权限。

每个提交操作至少包含默认、校验失败、提交中、提交成功和提交失败。审核中、部分成功、冲突或离线等状态只在业务需要时增加。

## 12. 文案与数据格式

- 默认使用简体中文，同一业务对象只能有一个正式名称。
- 文案简短、直接并说明下一步，不用“亲”“哎呀”等娱乐化表达。
- 日期默认使用 `YYYY-MM-DD`，日期时间使用 `YYYY-MM-DD HH:mm`；跨时区业务必须显示时区。
- 金额必须显示币种或货币符号，并按业务精度格式化；不得只显示无单位数字。
- 大数字使用千位分隔；百分比明确小数位规则；空值统一显示 `—`，不得混用空字符串、`null` 和 `N/A`。
- 确认和错误文案应引用具体对象，不能只有“操作失败，请重试”。

## 13. 图标、图片和可视化

- 新项目统一使用 `@ant-design/icons` 6；现有项目继续使用已经确认的单一图标体系，不用 Emoji 代替业务图标。
- 默认使用简洁的线性图标：行内图标 `16px`、按钮图标 `18px`、区块图标 `20px`、空状态图标 `28–32px`；项目已有体系时按其等价尺寸映射。
- 不得引入第二套图标库；缺少特殊业务图标时先复用项目资产，新增依赖须获得批准。
- 图标不能单独承担复杂含义；不熟悉的图标必须配文字或提示。
- 后台页面不使用无业务价值的装饰图、人物插画和大面积背景图。
- 图表必须有标题、单位、图例和数据来源；颜色之外还应使用标签、线型或形状区分类别。
- 关键数据不能只存在于图表中，应提供数值、摘要或可访问的替代信息。

## 14. 可访问性

项目默认达到 WCAG 2.2 AA，最低要求如下：

- 优先使用原生 `button`、`a`、`input`、`table` 等语义元素；不能用 `div` 模拟可交互控件。
- 所有关键功能可仅使用键盘完成，焦点顺序与视觉顺序一致，焦点样式清晰且不被遮挡。
- 表单标签、错误信息、图标按钮和动态反馈必须具有可访问名称或关联关系。
- 自定义菜单、标签页、树、对话框和组合框必须遵循对应的 WAI-ARIA Authoring Practices 键盘模型。
- 目标区域至少满足 WCAG 2.2 的 `24 × 24 CSS px` 要求；SEEKWAY 后台控件默认不小于 `34px` 高。
- 不得仅依赖颜色、位置、形状、声音或悬停表达关键信息。
- 页面缩放到 `200%` 后仍可阅读和操作，文本不得被截断到无法理解。

## 15. 工程与执行边界

React、TypeScript、代码职责和依赖约束见 `docs/codex/frontend.md` 与 `docs/codex/code-quality.md`；开发流程和验证要求见 `docs/codex/workflow.md` 与 `docs/codex/verification.md`。

新项目基线只包含 Ant Design 6 和 `@ant-design/icons` 6，不含 `@ant-design/pro-components`、其他 UI 库、CSS 框架或可视化库。通用组件直接使用 Ant Design；只为稳定复用的业务规则抽取业务组件。

界面任务必须逐项执行下方验收清单。未检查的视觉、交互或可访问性项目必须报告为未验证。

## 16. 界面验收清单

- [ ] 页面目标和主操作明确，一个区域不超过一个主按钮。
- [ ] 复用了项目设计令牌、基础组件、图标和相似页面模式。
- [ ] 采用公司基线时，根级 `ConfigProvider`、Ant Design `App` 上下文、中文环境和 SEEKWAY 主题已经生效；现有主题系统已验证其等价入口。
- [ ] 标题、筛选、操作、数据和分页的层级及位置一致。
- [ ] 加载、空数据、筛选无结果、失败、无权限和正常状态完整。
- [ ] 表单标签、校验、单位、提交中和失败反馈完整。
- [ ] 危险操作说明了对象、影响和可恢复性。
- [ ] 目标视口下没有意外横向滚动、遮挡和不可操作区域。
- [ ] 文字、数字、金额、日期、枚举和空值格式一致。
- [ ] 可仅使用键盘完成关键路径，焦点清晰且不被遮挡。
- [ ] 颜色对比度、目标尺寸和语义结构达到 WCAG 2.2 AA。
- [ ] 未混入第二套 UI 或图标体系，未依赖 Ant Design 内部 DOM、内部类名或高优先级全局覆盖。
