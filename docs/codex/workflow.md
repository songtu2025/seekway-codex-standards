# Codex 开发流程与项目边界

涉及代码、项目结构、配置、依赖、部署、项目文档或生产边界时，必须读取本文件。本文件与根目录 `AGENTS.md` 冲突时，必须先修正规则。

## 1. 技术与环境基线

以下基线适用于新项目。现有项目以已确认的技术栈和运行环境为准，并在 README 或根目录 `AGENTS.md` 中记录差异。

- 开发环境：Windows
- 代码托管：GitHub
- 生产环境：阿里云 ECS
- 前端：React 18 及以上、TypeScript、Vite；新 Web 项目默认使用 Ant Design 6 和 `@ant-design/icons` 6
- 后端：Python、FastAPI、Pydantic、SQLAlchemy、Alembic、pytest、Ruff，以及项目选择的 Mypy 或 Pyright
- 部署：Docker、Docker Compose、Nginx

Ant Design 6 和 `@ant-design/icons` 6 是新 Web 项目已批准的基线依赖。未经批准，不得更换现有框架、组件库、数据库或部署方案，也不得增加其他生产依赖和基础设施。现有项目不因该基线迁移组件库或主题系统。

## 2. 标准项目结构

新项目默认采用前后端分离、同一仓库管理的结构：

```text
project-name/
├── AGENTS.md
├── README.md
├── .env.example
├── .gitignore
├── compose.yaml
├── docs/
│   └── codex/
├── frontend/
│   ├── package.json
│   ├── src/
│   └── tests/
├── backend/
│   ├── pyproject.toml
│   ├── alembic.ini
│   ├── app/
│   ├── migrations/
│   └── tests/
├── deploy/
└── .github/
    ├── workflows/
    ├── ISSUE_TEMPLATE/
    ├── pull_request_template.md
    └── CODEOWNERS
```

新项目目录要求：

1. 前端代码放在 `frontend`，后端代码放在 `backend`，项目文档放在 `docs`。
2. 数据库迁移放在 `backend/migrations`，部署配置放在 `deploy` 或根目录，GitHub 配置放在 `.github`。
3. 未经批准不得改变一级目录结构；项目不需要的二级目录可以省略。
4. 不得提交临时文件、日志、数据库文件和真实业务数据。

现有项目保持原有结构和兼容性，不为套用模板重命名目录或全量重构。

## 3. 既有项目规范接入

项目已有规则或贡献指南时，不得用公司模板整文件覆盖。公司规范是默认基线，已验证的业务、架构和工具约束是项目事实。接入前必须完成审计并获得确认。

### 3.1 只读审计

修改规则前必须：

1. 读取根目录及相关子目录的 `AGENTS.md`，确认作用域，并检查 `AGENTS.override.md`、README、贡献指南和专项规范。
2. 从代码、配置和自动化入口核对技术栈、目录、启动、检查和部署方式。
3. 将现有规则分为保留、重复、疑似过时、冲突、目录特有、低频专项和公司规范缺失。
4. 说明修改文件、合并方式、风险和验证方法；无法确认的规则保持不变并请求确认。

### 3.2 分类与合并

| 规则类型 | 处理方式 |
| --- | --- |
| 项目业务事实、架构边界、禁止事项和真实检查命令 | 保留，并以项目实际情况为准 |
| 与公司规范含义相同的规则 | 只保留一个事实来源，删除重复表述 |
| 已由项目工具稳定强制执行的格式和静态规则 | 保留工具、配置和执行命令，不在始终加载的文件中逐条复述 |
| 只影响一个目录的规则 | 放入该目录已有或必要的嵌套 `AGENTS.md`，不得在根文件重复 |
| 低频或任务专项流程 | 放入现有专项文档，并在根文件说明准确的读取条件 |
| 有证据确认已经失效的规则 | 说明证据和影响后删除 |
| 无法确认真伪的规则 | 保留并请求确认，不得自行删除 |
| 项目不使用的公司默认技术或流程 | 不复制，并在必要时记录为不适用或项目差异 |

合并时补充缺失的安全和生产底线，但不得机械追加完整模板、改变已确认的技术栈或统一目录。

### 3.3 冲突处理

1. 法律合规、数据安全、权限、生产数据库、生产发布和破坏性操作采用更严格规则，不得通过项目差异放宽。
2. 项目实际技术栈、目录、包管理器、测试框架、部署方式和已验证设计系统优先于公司默认值。
3. 根规则与子目录规则冲突时，子目录规则只在其目录作用域内优先，并应明确说明例外原因。
4. 规则无法同时满足或证据不足时，列出双方规则、项目证据、影响和建议，获得确认后处理。

### 3.4 规则文件边界

父级规则与路径上的子级规则累积生效。嵌套 `AGENTS.md` 只补充目录特有的命令、架构或安全约束，不重复父级规则。

同一目录存在 `AGENTS.override.md` 时，Codex 不加载同目录的普通 `AGENTS.md`。该文件只用于明确的替换场景，不得用来追加公司规则；未经确认不得新增、删除或替换。

全局 `AGENTS.md` 只适合保存稳定的跨项目偏好和底线；项目正确交付所需的业务、架构、检查和安全规则必须随仓库维护，不得依赖某位开发者的全局配置。

普通 Markdown 文件不会自动加入规则链。根文件必须用“触发条件 + 路径”建立索引；项目已有等价文档时直接索引，未同步的专项规范不得保留索引。

### 3.5 规模、版本与升级

新项目根目录 `AGENTS.md` 以 100 行以内为目标。现有项目超出目标时，先删除重复和失效内容，再按作用域和加载频率渐进迁移；不得仅因行数删除有效规则或阻塞必要修改。

Codex 当前默认最多组合 32 KiB 项目规则。接近限制时，先减少重复、缩小始终加载范围或按目录分层，不得用提高限制代替治理。加载行为以 [Codex 官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md) 为准。

项目 README 必须记录规范基线版本、接入日期和项目差异。升级时将变更分为适用、不适用、已存在和冲突，只合并适用且缺失的内容，再更新基线版本。

## 4. 开始开发前

修改代码前必须：

1. 按 `AGENTS.md` 索引读取相关专项规范，并阅读 README、需求、相关代码和测试。
2. 检查调用链、现有实现和可复用能力。
3. 复述需求、验收标准和不做的事项。
4. 列出修改文件、影响内容及数据库、认证、权限、配置、依赖和部署影响。
5. 说明风险、回滚方式和验证方案。
6. 非简单任务获得确认后再修改。

涉及 Web 界面时，还须读取 `docs/codex/frontend.md` 和项目的 `docs/web-ui-standard.md`，再按核心规范中的触发条件读取布局、表单或数据专项规范；缺失时读取对应模板并报告。检查已有令牌、组件、布局和相似页面，明确设计来源、目标视口及页面状态。新项目采用 Ant Design 基线；现有项目改用该基线前必须确认。

## 5. 修改范围

必须：

1. 只修改完成当前任务所必需的文件，保持现有业务规则、接口和兼容性。
2. 复用已有代码和实现模式，新增或修改业务逻辑时补充必要测试。
3. 发现无关问题时只记录，不顺带修改。

不得：

1. 自行增加功能、页面、接口、业务规则或需求中没有的业务字段。
2. 进行与当前任务无关的重构或修改无关文件。
3. 擅自删除已有功能、接口、字段或数据。
4. 擅自修改公共模块、认证、权限或部署配置。
5. 为“以后可能使用”提前增加代码、字段或组件。
6. 在多处维护同一业务规则。

## 6. 安全与生产边界

不得主动读取、生成、提交或传播：

- 真实密码、Token、AccessKey、SecretKey 和私钥。
- 生产环境变量的真实值。
- 未脱敏的真实业务数据。
- 包含真实敏感信息的数据库文件、日志、上传文件和导出结果。

可以读取和处理：

- 认证相关的代码、字段名和配置结构。
- 不包含真实凭据的 `.env.example` 和占位值。
- 测试数据、模拟数据和已经脱敏的数据。
- 用户明确提供且不包含真实敏感信息的需求附件、示例文件和设计资料。

允许使用不显示命中值的工具扫描源码和提交记录。发现真实敏感信息时，停止处理并提醒用户，不得复述其值。生产数据库和生产迁移只能由部署负责人操作。

## 7. 项目文档

创建或维护项目时，README 至少包含：

- 项目用途、适用范围和明确不做的事项。
- 技术栈、系统架构和关键业务规则。
- 本地启动、测试和构建方式。
- 部署文档入口。

根目录 `AGENTS.md` 至少包含业务边界、Codex 修改规则、禁止修改内容、专项规范索引、必须执行的检查以及数据和 Git 安全要求。重要业务规则不得只存在于聊天记录或个人记忆中。
