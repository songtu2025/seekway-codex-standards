# Codex 界面设计发现与探索规范

新建 Web 界面或原型、明显重设计，或界面方向不明确时必须读取。本文件负责设计决策；组件、令牌、布局和可访问性仍按项目 Web UI 规范执行。

## 1. 原则与适用范围

模型生成服从上下文条件下的分布，提示中的“随机”不保证均匀抽样；增加数量、提高温度和重复要求创新，也不能单独证明结构覆盖。模型具有多种方案的表达能力，不代表一次生成能覆盖这些方向。外部采样只控制已定义选项的选择，不能补回空间中遗漏的方向，也不保证设计质量。

空间定义、候选解释和筛选都须留下可核对的依据，避免同一种偏好贯穿所有环节。探索与筛选分开进行，先确定真实任务和约束，再比较方向；不得把生成概率、模型自报概率或熟悉程度当作设计价值。

| 任务 | 执行范围 |
| --- | --- |
| 现有模式内的局部修复 | 沿用现有设计，验证受影响状态；不要求多方案和采样 |
| 新页面已有适用且经过验证的模式 | 说明任务、复用依据和差异后实施；有未解决的设计问题再展开探索 |
| 提供明确设计稿、要求还原 | 核对任务、状态和约束，按稿实现；冲突先确认，不擅自改成其他方向 |
| 只要求视觉改进且方向模糊 | 翻译感觉层需求，比较构图、字阶、密度和视觉强调；保持已确认的业务与交互 |
| 新工作台、编辑器或明显重设计，结构与操作方式不明确 | 建立任务模型与设计空间，执行覆盖安排、候选筛选和任务原型验证 |

产物优先在对话和现有任务说明中表达。需要跨阶段复核时，在同一设计记录中维护输入、采样和决策，不按生成次数新建文件；无继续使用价值的临时产物按任务结束清理。

## 2. 意图翻译与任务发现

1. 保留用户原话，将“高级”“科技感”“有设计感”等表达转成候选解释，说明与当前产品的关系；不得要求用户掌握专业术语，也不得套用“高级必然黑白”等固定对应。
2. 说明每种解释将改变哪些可观察变量，例如信息层级、字阶、留白、视觉噪音和操作强调，以及怎样判断是否符合用户意图。
3. 理解目标用户、关键任务、使用频率、数据规模、操作环境、成功标准和现有品牌。问题只围绕会改变方案的未知事项；未知偏好可用简短对比帮助用户发现。
4. 区分已确认事实、推测和待验证假设。不得借方案补充未经确认的业务能力，例如为了形成“AI 驱动”方向擅自增加自动决策。

所有候选保持相同目标、关键任务、数据和硬约束。更换产品目标不算同一任务的设计发散。

## 3. 约束与设计空间

### 3.1 先核对约束

- 业务规则、权限、安全、可访问性和已确认的品牌要求属于硬约束。
- 默认侧栏、页面骨架、信息密度等属于基准方案，除非已被当前项目明确确认为不可改变的边界。
- 已确认采用的现有布局是局部任务的边界；用户要求重设计时，先明确允许改变的部分。
- 探索中改变默认布局不代表获准采用。方向确认后，将差异同步到项目界面规范，再实现。

### 3.2 显式建立空间

按任务选择有意义的维度，不照搬固定维度表。结构探索可涉及任务组织、信息架构、导航、工作区、操作路径和密度；视觉探索可涉及构图、字阶、节奏、材质和强调方式。每个维度与选项须说明来自任务事实、既有基准、参考案例还是待验证假设。

建立空间后必须检查：

1. 哪些默认前提尚无任务依据，例如“工作台必须有固定侧栏”。
2. 是否只列出了同一类界面的局部变体，是否遗漏时间、对象关系、队列、直接操作等与任务有关的组织方式。
3. 是否只是更换名称，实际上具有相同操作路径；选项之间是否存在重叠或依赖。
4. 哪些组合不成立，依据是什么；未验证的困难不能直接写成硬排除条件。
5. 某类方向是否因被拆成更多选项而获得更多探索机会；各类机会由分组安排决定，不声称整个设计空间均匀。

采样前保留可审查的空间版本。发现遗漏、语义重复或错误排除时，修订空间并说明原因后重新运行；不得静默删除维度、修改配额或放宽硬约束。

## 4. 覆盖安排与程序采样

### 4.1 安排方向

保留一个符合任务约束的基准。完整探索还须明确不同结构方向、边界方向和挑战默认前提的方向；每项写明想验证的问题。正交、边界和反先验是探索方法，不是模型偏差已经消除的证明。

正交方向须在重要任务或设计维度上产生有意义的差异，不要求数学上的独立；边界用来检查适用范围，反先验用来检验常见前提。限制常见模式只作用于相应探索分组，不成为全项目禁令。方法重叠时可复用方向，但须说明实际覆盖；不得用不合理方案凑数。

需要时使用逆向探索反转可调整的默认方式，或通过反事实探索移除尚未证实的前提；两者仍保持同一任务和硬约束。只采用能回答当前设计问题的方法，不机械要求每次执行全部方法。

候选数量是预算。先生成简短组合与操作路径，核对覆盖后再深化；不要求每个候选都做完整原型，也不固定“20 个必然筛成 3 个”。连续生成没有新增有意义的方向时，审查空间和约束，不继续堆数量。

### 4.2 工具与配置契约

规范源仓库提供 `templates/design-exploration/`。需要程序采样时，将 `sample.py`、`space.py` 和任务所需配置按需复制到业务项目的 `scripts/design-exploration/`，或复用已有等价工具；记录实际路径。示例是合成场景，选项与排除理由均须按任务核对，不直接成为业务规则。工具需要 Python 3.10 及以上，只使用标准库，不属于应用运行时依赖。

| 配置字段 | 含义 |
| --- | --- |
| `schema_version`、`scope`、`task` | 版本为 1；范围为 `structure` 或 `visual`；所有组合服务于同一任务 |
| `constraints` | 待人工核对的文字约束；程序不会自动理解或执行这些文字 |
| `axes` | 每项有唯一 `id`、`label`、`kind`、`source` 和非空不重复的 `options`；`kind` 为 `core` 或 `visual` |
| `baseline` | 所有维度的基准选项，必须符合编码排除条件；程序单独保留该组合 |
| `exclusions` | 每项有 `match` 与 `reason`；条件对象中的维度全部命中才排除 |
| `groups` | 每项有唯一 `id`、`purpose`、`minimum`、`patterns` 和可选 `min_changes`；基准不计入配额 |

分组的多个 `patterns` 是“任一满足”。需要分别覆盖两个边界时，建立两个分组；一个分组配额为 2 不保证两个条件各出现一次。空条件对象表示不限选项。`min_changes` 是相对基准的编码差异数量，只比较本轮的核心或视觉维度。`baseline` 和 `coverage` 是保留分组名。

工具先枚举符合编码约束的组合，再匹配分组配额，最后补充未覆盖选项和编码差异；同分取舍使用带种子的伪随机顺序。组合总数超过 50000，或候选预算超过 200 时须缩小本轮空间或分轮处理，避免枚举和距离矩阵无限增大。这不是整个设计空间的均匀随机抽样。

在规范源仓库运行：

```sh
python -B templates/design-exploration/sample.py --space templates/design-exploration/example.json --seed 41382 --count 16
```

工具只向终端输出 JSON：包含原配置及摘要、种子、工具和 Python 版本、候选、覆盖、编码距离、同签名候选和不足项。同一配置、种子、预算、工具及运行环境可以复现；跨版本须重新核对。需要保留时将结果纳入当前设计记录，不自动为每个候选创建文件。

退出码 `0` 表示数量与配额满足，`1` 表示配置无效，`2` 表示可用组合或分组配额不足，且仍输出不足记录。`sampling_complete` 不代表空间覆盖完整、文字约束满足或设计通过。预算内未覆盖的可行选项与编码约束下不可用的选项分开报告。

程序不可用时，采用显式列举与覆盖表并说明未使用随机采样；不得让模型编造种子、运行结果、生成概率或覆盖统计，也不得将自主列举描述成均匀随机。

## 5. 候选解释、筛选与用户比较

每个组合先解释为简短方案：关键任务如何进入、处理和结束，信息如何组织，反馈如何出现。逐项核对解释与组合是否一致；无法解释的组合标记问题，修订或淘汰并说明原因，不悄悄换回基准。编码不同但真实操作相同的方案合并；编码距离不能替代体验差异判断。

给用户展示前，按以下顺序筛选并记录依据：

1. 核对真实任务和硬约束，指出违反的具体要求。
2. 核对组合能否成立；区分确认不成立、实现成本高和仍待验证。
3. 合并真实任务路径或视觉表达重复的方案，保留有价值的差异。
4. 分别评估可用性、新颖性、学习成本和实现成本，不用模型自评分或熟悉程度作唯一依据。
5. 保留有潜力但证据不足的方向，选取能降低不确定性的最小原型；不能仅因少见、偏离默认侧栏或描述不够流畅而删除。

复用当前任务说明，以候选编号记录组合、解释、保留或淘汰结论、具体依据和待验证项。改变输入后的记录须能区分版本，不能覆盖原结果后声称未改变空间。

最终展示数量由有效方向决定，可少于预期并说明原因。比较表须包含相同关键任务下的操作路径、重要结构或视觉差异、适用条件、代价和验证问题；同时提供可读的结构草图或最小原型。不得把第一个生成的方案自动列为最佳，也不得将有偏好差异的方案包装成客观评分排名。

## 6. 选定方向、视觉表达与验证

用户确认方向后，将感觉层意图转成视觉表达：说明构图、字阶、密度、色彩强调、图像与动效如何服务于任务和受众，再映射到现有设计令牌与组件。保留可识别的视觉重点，避免无依据地套用同一种卡片、渐变或装饰组合；不以反常或装饰数量判断设计质量。

按 `docs/codex/frontend.md` 处理原型与合成数据，按 `docs/codex/workflow.md` 衔接接口契约和真实闭环。关键原型使用相同任务、数据和视口比较操作、查找、阅读、学习与错误恢复；记录用户反馈和仍未验证的假设。模型评审须引用这些依据，不能替代实际操作验证。

最终界面按项目 Web UI 规范检查视觉层级、一致性、各类状态、键盘、对比度和响应式，并对照选定方向核对实现。工程与设计决策的完成检查集中在 `docs/codex/verification.md`；未经原型或实际使用验证，不声称提升了业务效率或审美质量。

## 7. 依据与研究边界

- [Verbalized Sampling](https://arxiv.org/abs/2510.01171)：研究偏好数据的典型性偏差及生成多样性干预，不证明特定前端设计有效。
- [Examining and Addressing Barriers to Diversity in LLM-Generated Ideas](https://arxiv.org/abs/2602.20408)：研究生成固着和知识分区；具体效果受模型、任务及方法影响。
- [Judging LLM-as-a-Judge](https://arxiv.org/abs/2306.05685)：评审模型存在位置、冗长和自我偏好等偏差，模型评价须结合独立证据。

本文件的覆盖安排、配置与筛选记录是基于上述问题提出的工程做法，实际设计效果须通过项目验证，不把研究结论扩大成所有模型的固定规律。
