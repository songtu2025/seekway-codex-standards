# Codex 代码质量与拆分规范

新增、修改、重构或评审代码时，必须读取本文件。规则适用于所有进入仓库的代码。

## 1. 设计原则

1. 保持高内聚、低耦合，每个模块只承担清晰且相关的职责。
2. 保持依赖方向清晰，避免循环依赖和跨层调用。
3. 使用准确命名和简单控制流程，使代码便于阅读、测试、修改和定位问题。
4. 隐藏内部实现，只暴露协作所需的最小接口。
5. 复用已有业务规则，但不为复用而过早抽象。
6. 遵循项目已有结构和实现方式。
7. 密码、密钥、地址、端口、路径和环境参数必须通过配置或环境变量管理。
8. 重复使用或可能变化的业务状态、类型、阈值和固定值使用具名常量、枚举或集中配置；含义固定且仅局部使用的值可以直接书写。

## 2. 规模、复杂度与拆分

可维护性取决于职责、依赖、复杂度、可修改性和可测试性。行数只是预警信号，不能单独决定是否拆分或完成任务。

1. 模块、类、组件或函数包含多个独立变化的职责时，按业务边界拆分。
2. 文件超过 500 行时必须检查职责数量、依赖关系、复杂度和测试方式；仅有行数较多不得作为强制拆分理由。
3. 文件超过 800 行时，必须在实施方案中说明当前职责、复杂逻辑位置、拆分可行性和测试影响。
4. 新文件预计超过 1000 行，或本次修改使文件首次超过 1000 行时，实施前必须提出拆分方案；不宜拆分时说明原因并获得确认。
5. 现有超长文件不阻塞局部修复；本次修改不得加入无关职责，独立的新能力应放入职责明确的模块。
6. 函数只完成一个明确目标。函数超过 50 行时必须检查复杂度和职责，不得仅为减少行数提取无业务含义的辅助函数。
7. 函数默认阈值：圈复杂度不超过 10、分支数不超过 12、语句数不超过 50、嵌套块不超过 5、位置参数不超过 5；项目已有认知复杂度检查时默认不超过 15。
8. 函数超过阈值时，先简化流程、拆分职责或调整数据结构；无法降低时在实施方案和完成报告中说明原因。
9. React 页面和组件应分别检查数据获取、业务状态、表单、弹窗、表格配置和页面区域；混合多个独立职责时必须拆分，不以行数较少为例外。
10. 自定义 Hook 只封装内聚且可复用的状态或副作用，不得用整体搬移复杂逻辑来规避组件复杂度。
11. 拆分后不得产生循环依赖、重复规则、空壳转发层、过度参数传递或难以追踪的文件碎片。
12. 单次变更新增和修改接近或超过 1000 行时，优先拆为可独立验证的阶段；无法拆分时，实施前说明原因并获得确认。
13. 功能修改与大范围重构原则上分开；重构是需求前提时，必须说明范围和回归风险。
14. 新增和修改不得降低代码健康度，但局部需求不必一次性治理全部遗留代码。
15. 完成后检查涉及文件的职责、规模和函数复杂度，报告预警、处理结果和未处理原因。

## 3. 注释与清理

注释用于解释业务规则、设计原因、边界条件、兼容要求和风险，不重复代码本身。

完成任务后必须：

1. 检查本次新增代码是否重复已有实现。
2. 删除因本次修改而失效的旧代码。
3. 删除不再使用的 import、export、函数、组件和依赖。
4. 删除仅为“未来可能使用”而保留的代码。
5. 使用项目已有工具检查重复、死代码和循环依赖；没有工具时人工检查并如实报告。
